# 第一层：软件环境（5 个）

## 坑 1　Python 版本门禁拦住一键安装

**现象**
```
ERROR: Package 'mindspeed-mm' requires a different Python: 3.11.15 not in '<3.13,>=3.12'
```

**根因**：`pyproject.toml` 声明 `requires-python = ">=3.12,<3.13"`，镜像只有 3.10 与 3.11.15。
**不能升到 3.12** —— torch_npu 2.10.0 是为 3.11 构建的，换解释器会直接毁掉唯一可用的 NPU 运行环境。

**解法**：只放宽门禁，不动解释器。
```bash
sed -i 's|requires-python = ">=3.12,<3.13"|requires-python = ">=3.11,<3.13"|' pyproject.toml
```
→ 脚本 `02_env.sh` 第 5 步

## 坑 2　transformers 版本冲突导致依赖装不进去

**现象**
```
mindspeed-mm 0.1 depends on transformers==4.57.0
The user requested (constraint) transformers==5.2.0
ERROR: ResolutionImpossible
```

**根因**：`pyproject.toml` 把 transformers 钉在 4.57.0，但 Qwen3.5 是 2026-02 的新模型，官方 `install_extensions.sh` 第一行就是 `pip install transformers==5.2.0`。两者不可调和，所以 `pip install -e .` **永远不可能成功**。

**解法**：放弃整体安装，改用约束文件保护关键版本 + 按名单补装。
```bash
printf 'transformers==5.2.0\ntorch==%s\ntorch_npu==%s\nnumpy==%s\n' "$T" "$N" "$U" > /tmp/ascend_constraints.txt
python -m pip install -c /tmp/ascend_constraints.txt \
  accelerate datasets ftfy "jsonargparse[signatures]" numba peft pydantic \
  qwen_vl_utils torchdata megatron-core diffusers
```

**注意**：`jsonargparse` 必须带 `[signatures]`，否则 `mm-convert` 报
`ImportError: docstring-parser is required by _set_docstring_parse_options`。

**忽略**：此后每条 pip 都会顶一句 `requires transformers==4.57.0, but you have 5.2.0`，属预期。
→ 脚本 `02_env.sh` 第 6-7 步

## 坑 3　`ModuleNotFoundError: No module named 'megatron'`

**根因**：不是环境缺件。`mindspeed_mm/__init__.py` 自带守卫：
```python
if os.getenv("NON_MEGATRON", "") != "true":
    from mindspeed_mm.tasks.finetune.lora import lora_patch
```
插件式 FSDP2 路线（入口 `fsdp/train/trainer.py`）**本就不走 Megatron 桥接**。

**解法**
```bash
export NON_MEGATRON=true      # 并写入 ~/.bashrc
```
→ 脚本 `common.sh` 的 `ensure_env()`

## 坑 4　triton-ascend JIT 编译与 CANN 9.0.0 不兼容

**现象**
```
RuntimeError: Failed to compile /tmp/xxx/npu_utils.cpp:321:44:
error: 'RT_LIMIT_TYPE_SIMT_WARP_STACK_SIZE' is not a member of 'rtLimitType_t'
```

**定位过程（三步排除）**
1. 怀疑 megatron-core 版本 → **排除**（`SIMT_WARP_STACK_SIZE` 在 megatron/mindspeed/torch_npu 里一处都搜不到）
2. 怀疑 torch_npu 与 CANN 配错 → **部分成立但非致命**（基本 NPU 张量运算完全正常）
3. 全盘搜 `RT_LIMIT_TYPE` → **命中** `triton/backends/ascend/npu_utils.cpp`

**根因**：triton-ascend 编译 Ascend kernel 前会现场 JIT 编译 `npu_utils.cpp`，用 `rtDeviceSetLimit()` 设 `WARP_STACK_SIZE` 等设备限制。其中 `RT_LIMIT_TYPE_SIMT_WARP_STACK_SIZE` 在 CANN 9.0.0 的 `rt_external_base.h` 里不存在（只定义到 `RT_LIMIT_TYPE_STACK_SIZE = 3`）。

**解法**：删掉引用该枚举的行。
```bash
python3 lib/patch_triton.py      # 按内容匹配删除，幂等
```

> **重要更正**：旧环境当时判定「triton 走不通」而全线退回 eager。
> 实际上打掉这两行后 triton 是可用的，所以本包**多留了 triton 一档**做对比。
> 而且 ascendc 模式下 `causal_conv1d_implementation` 只支持 triton/ascendc，
> 所以这个补丁是 ascendc 路径的**必要前提**。

→ 脚本 `lib/patch_triton.py`、`02_env.sh` 第 10 步

## 坑 5　`eager` 与 `skip_*_recompute` 互斥

**现象**
```
ValueError: skip_flash_attn_recompute cannot be True when gdn_implementation is 'eager'.
```

**根因**：上游配置里 `skip_gdn_recompute` / `skip_flash_attn_recompute` 都是 `true`，这是配合 ascendc/triton 的跳过重计算优化；换成 eager 后不再成立。

**解法**：两个都设 `false`（同类开关一起改）。
```python
cfg["model"]["skip_gdn_recompute"] = False
cfg["model"]["skip_flash_attn_recompute"] = False
```
→ 脚本 `scripts/run_round.sh` 的配置生成段（按 mode 自动配对）

# 第二层：运行环境（5 个）

## 坑 6　配置相对路径 × 工作目录错位

**现象**：训练报找不到 `./ckpt/...` / `./dataset/...`

**根因**：配置里用相对路径，而训练的工作目录是仓库根 `MindSpeed-MM/`。
另外 `ckpt` 原本已存在一个**空目录**，会被误判为"已存在"而跳过建链接。

**解法**
```bash
cd /workspace/ascend_ws/MindSpeed-MM
rmdir ckpt && ln -s /workspace/ascend_ws/ckpt ckpt
ln -s /workspace/ascend_ws/dataset dataset
```
→ 脚本 `02_env.sh` 第 11 步、`04_assets.sh` 第 4 步

## 坑 7　`install.sh` 无 stdin 时死循环

**现象**：MindSpeed-MM 的 `scripts/install.sh` 在无交互环境下疯狂刷日志，**曾刷出 3.8GB**。

**解法**：必须带 `--no`。
```bash
cd MindSpeed-MM && timeout 1500 bash scripts/install.sh --msid eb10b92 --no
```
→ 脚本 `02_env.sh` 第 4 步

## 坑 8　镜像装不了 tmux，且 apt 依赖树已损坏

**现象**
```
apt-get install tmux → E: Unmet dependencies (libc6 / libtinfo6 / python3-minimal 冲突)
```

**红线**：**绝对不要执行 `apt --fix-broken install`** —— 它要动 `libc6`，可能直接毁掉容器，卡时白烧。
**解法**：改用 `nohup` + `&` 跑后台任务。

## 坑 9　pip 清华源返回 403

**解法**：换华为云。
```bash
pip config set global.index-url https://repo.huaweicloud.com/repository/pypi/simple/
```
→ 脚本 `02_env.sh` 第 1 步

## 坑 10　排查失败不能用 `tail`

**现象**：torchrun 失败时打印约 25 行统一格式报告，会把真正的 Python traceback 顶出 `tail -30` 的窗口。

**解法**：用 `awk` 抓第一个 traceback。
```bash
awk '/Traceback \(most recent call last\)/{f=1} f{print; n++} n>50{exit}' 日志
```
→ 脚本 `whats_wrong.sh`

# 第三层：fla_npu 编译链（6 个，旧环境后期才踩到）

## 坑 11　`gawk: command not found`（exit 127）

**现象**
```
build.sh: line 1933: gawk: command not found
```

**根因**：镜像只有 `mawk`，而 `build.sh` 用 gawk 的 `strftime()` 扩展生成版本号时间戳。
**不能 apt 装 gawk**（apt 依赖树已坏，见坑 8）。

**解法**：造 gawk 替身 —— 拦下 awk 程序体里的 `strftime("fmt")`，用 Python 先算成字面量再交给 mawk。
```bash
cp patches/gawk_shim.sh /usr/local/bin/gawk && chmod 755 /usr/local/bin/gawk
```
→ 脚本 `patches/gawk_shim.sh`、`02_env.sh` 第 2 步、`03_fla_npu.sh` 第 0 步

## 坑 12　`FileNotFoundError: libcust_opapi.so`

**现象**：加载 fla_npu 时报找不到 `libcust_opapi.so`；`opp/vendors/` 下只有 `README.txt`。

**根因**：fla_npu 的 OPP 算子包**从未编译成功过**（`.run` 包是空的）。
**判据**：`torch.ops.npu` 里算子总数只有 354 且没有 `npu_recompute_w_u_fwd`。

**解法**：从零编译。
```bash
bash build.sh --pkg --soc=ascend910_93 --vendor_name=fla_npu -j16 -O3
# 约 23 分钟，产出 build_out/fla_npu_linux-aarch64.run（41.8 MB）
bash build_out/*.run
```
**关键**：SoC 必须显式写 `ascend910_93`（不是 `ascend910b`，也不是 `ascend910_9382`）。
→ 脚本 `03_fla_npu.sh` 第 3-4 步

## 坑 13　`AttributeError: 'npu' object has no attribute 'npu_recompute_w_u_fwd'`

**根因**：该算子靠 `libfla_npu_stable.so`（752 KB）注册，而这个文件没编出来。
**试过但无效**：`export ASCEND_CUSTOM_OPP_PATH=...`（算子数仍 354）。

**解法**：编 `torch_custom/fla_npu`，产出 `libfla_npu_stable.so`。
→ 脚本 `03_fla_npu.sh` 第 5 步

## 坑 14　`custom_aclnn_extension_lib*.so` 找不到

**现象**
```
load_legacy_torch_ops() → not find custom_aclnn_extension_lib*.so
```

**定位链**：`setup.py` 有 `ext_modules` 定义 → `get_sources()` 返回 2 个源文件（正常）
→ `setup()` 藏在 `_setup_legacy_extension()` 里 → **由 `FLA_NPU_BUILD_LEGACY_EXTENSION` 环境变量控制，默认为关**。

**解法**
```bash
FLA_NPU_BUILD_LEGACY_EXTENSION=1 python setup.py build_ext --inplace --force
```
→ 脚本 `03_fla_npu.sh` 第 5 步

## 坑 15　`FLANpuOpApi.cpp` 三处编译错误

**现象**
```
FLANpuOpApi.cpp:314:28: error: cannot bind non-const lvalue reference of type 'bool&' to an rvalue
FLANpuOpApi.cpp:742:31: error: 'layout_str' was not declared in this scope
FLANpuOpApi.cpp:985:34: error: cannot bind non-const lvalue reference of type 'int&' to an rvalue
```

**关键洞察**：编译日志里 11 条 `error:` 有 8 条在 torch_npu 头文件里（`'copied_params' is not captured`），
它们是上面三处的**次生报错**，修好前 3 处就自动消失 —— **不要动头文件**。

**解法**
| 错误 | 修法 |
|---|---|
| `bool&` 右值绑定 | 把字面量提成具名变量 `bool use_exp2_flag = <字面量>;` 插在该行前 |
| `'layout_str' 未声明` | 删除引用它的整行 |
| `int&` 右值绑定 | 提成 `int neg_one = -1;` |

→ 脚本 `lib/patch_fla_npu.py`（支持从编译日志自动解析修复）

## 坑 16　`undefined symbol: npu_fast_gelu_custom_backward`

**现象**
```
undefined symbol: _ZN6op_api29npu_fast_gelu_custom_backwardERK2at6TensorES3_
```

**根因**：`FLANpuPybind.cpp` 里**声明并注册**了 `npu_fast_gelu_custom` / `_backward`，
但 `FLANpuOpApi.cpp` 里**没有定义**（符号在 `op_api` 命名空间下）。

**解法**：在 `FLANpuOpApi.cpp` 的 `op_api` 命名空间内追加定义。
```cpp
at::Tensor npu_fast_gelu_custom(const at::Tensor &self) {
    at::Tensor out = at::empty_like(self);
    EXEC_NPU_CMD_EXT(aclnnFastGelu, self, out);
    return out;
}

at::Tensor npu_fast_gelu_custom_backward(const at::Tensor &grad, const at::Tensor &self) {
    at::Tensor out = at::empty_like(grad);
    EXEC_NPU_CMD_EXT(aclnnFastGeluBackward, grad, self, out);
    return out;
}
```
→ 脚本 `lib/patch_fla_npu.py` 的 P1

# 第四层：运行期（4 个）

## 坑 17　MindSpeed-MM 传参与 fla_npu 形参不匹配

**现象**：`TypeError: xxx() got an unexpected keyword argument 'save_new_value'`

**根因**：MindSpeed-MM 按上游 `flash-linear-attention` 的签名传参，会带
`save_new_value` / `use_exp2` / `transpose_state_layout`；
而 fla_npu 的算子包装层没有这三个形参（内部固定值）。

**解法**：兼容垫片，调用前丢掉这几个关键字。
**注意**：必须**静默**（每类参数只提示一次），否则刷屏会干扰性能数据测量和进度监控。

```python
import npu_ops_compat
npu_ops_compat.install()
```
→ 脚本 `patches/npu_ops_compat.py`

## 坑 18　训练把 CPU 吃满 → WebIDE 白屏 / SSH 连不上

**现象**：训练跑起来后 WebIDE 白屏，SSH 报 `504 Gateway Time-out`，等 20 分钟也不恢复。

**根因**：训练默认用满所有 CPU 核 + 大量内存，WebIDE 的 code-server 服务被饿死。
**注意**：这不是容器挂了，`/workspace` 数据完好 —— **不要因此去点「重置环境」**。

**解法**：用 `taskset` 限核，留 2 核给 WebIDE。
```bash
N=$(nproc); M=$((N>3 ? N-2 : 1))
taskset -c 0-$((M-1)) torchrun --nproc_per_node 1 ...
```
→ 脚本 `scripts/run_round.sh` 第 3 步

## 坑 19　SoC 型号必须显式指定

**解法**：`ascend910_93`（对应 Ascend910_9382）。
误写成 `ascend910b` 或 `ascend910_9382` 都会编译失败。
→ 脚本 `common.sh` 的 `SOC` 变量

## 坑 20　环境隔离：不同环境的 `/workspace` 不共享

**要点**
- 同一环境：关机 → 开机，`/workspace` **保留**
- 换环境：**完全隔离**，看不到原环境的任何文件
- 所以「新环境能打开」≠「有数据」

**红线**
- ❌ 不要点「重置环境」/「重建环境」（会清空容器）
- ❌ 不要新建/删除环境
- ✅ 只用 `/workspace`，不要用 `/root`（可能随容器重建消失）
- ✅ 收工去平台点「关机」（训练结束 ≠ 停止计费）

# 附：失败的排查顺序（照这个顺序，不要跳）
