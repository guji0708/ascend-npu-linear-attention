## 二、五个阻塞问题

### 问题 1：Python 版本门禁拦截一键安装

**现象**

```
ERROR: Package 'mindspeed-mm' requires a different Python: 3.11.15 not in '<3.13,>=3.12'
```

**根因**：`pyproject.toml` 声明 `requires-python = ">=3.12,<3.13"`，而镜像只有 Python 3.10 与 3.11.15。**不能升到 3.12** —— torch_npu 2.10.0 是为 3.11 构建的，换解释器会直接毁掉唯一可用的 NPU 运行环境。

**解法**：只放宽版本门禁，不动解释器。

```bash
sed -i 's/requires-python = ">=3.12,<3.13"/requires-python = ">=3.11,<3.13"/' pyproject.toml
```

### 问题 2：transformers 版本冲突导致依赖装不进去

**现象**

```
ERROR: Cannot install mindspeed-mm==0.1 because these package versions have conflicting dependencies.
  mindspeed-mm 0.1 depends on transformers==4.57.0
  The user requested (constraint) transformers==5.2.0
ERROR: ResolutionImpossible
```

**根因**：`pyproject.toml` 把 transformers 钉在 4.57.0，但 Qwen3.5 是 2026-02 的新模型，官方 `install_extensions.sh` 第 1 行就是 `pip install transformers==5.2.0` —— 必须 5.x 才识别该架构。两者不可调和，所以 `pip install -e .` **永远不可能成功**。

**解法**：放弃整体 `pip install -e .`，改用约束文件保护关键版本 + 按名单补装缺失依赖。

```bash
N=$(python -c "import torch;print(torch.__version__)")
P=$(python -c "import torch_npu;print(torch_npu.__version__)")
U=$(python -c "import numpy;print(numpy.__version__)")
printf 'transformers==5.2.0\ntorch==%s\ntorch_npu==%s\nnumpy==%s\n' "$N" "$P" "$U" > /tmp/ascend_constraints.txt

python -m pip install -c /tmp/ascend_constraints.txt \
  accelerate datasets ftfy jsonargparse numba peft pydantic qwen_vl_utils \
  torchdata megatron-core diffusers "jsonargparse[signatures]"
```

**注意 `jsonargparse` 必须带 `[signatures]` extra** —— 否则 `mm-convert` 报 `ImportError: docstring-parser is required by _set_docstring_parse_options`。这是 `pyproject` 里写成 `jsonargparse[all]` 而我们漏掉方括号导致的。

**忽略**：此后每条 pip 命令都会顶一句 `mindspeed-mm 0.1 requires transformers==4.57.0, but you have transformers 5.2.0`，属预期，不必处理。

### 问题 3：`ModuleNotFoundError: No module named 'megatron'`

**现象**

```
File ".../mindspeed_mm/__init__.py", line 3, in <module>
    from mindspeed_mm.tasks.finetune.lora import lora_patch
File ".../lora_patch.py", line 20, in <module>
    import megatron
ModuleNotFoundError: No module named 'megatron'
```

**根因**：不是环境缺件。`mindspeed_mm/__init__.py` 本身带守卫：

```python
1  import os
2  if os.getenv("NON_MEGATRON", "") != "true":
3      from mindspeed_mm.tasks.finetune.lora import lora_patch
4      from mindspeed_mm.patches import validate_args_patch
```

插件式 FSDP2 路线（入口 `mindspeed_mm/fsdp/train/trainer.py`）**本就不走 Megatron 桥接**，官方启动脚本第 8 行本来就设了 `export NON_MEGATRON=true`。测试时漏设该变量，才会走进 Megatron 分支。

**解法**

```bash
export NON_MEGATRON=true      # 并写入 ~/.bashrc，避免每个新终端重复踩
```

补充：MindSpeed-MM 的 `scripts/install.sh` 第 47 行 `INSTALL_MEGATRON=false` 是默认值，只有 `-mt` 参数才装 Megatron-LM —— 官方一键安装本身就不装它，进一步印证这条路不需要 megatron。

### 问题 4：triton-ascend 的 JIT 编译与 CANN 9.0.0 不兼容（最耗时的一个）

**现象**

```
RuntimeError: Failed to compile /tmp/tmpwys2mij1/npu_utils.cpp:321:44:
error: 'RT_LIMIT_TYPE_SIMT_WARP_STACK_SIZE' is not a member of 'rtLimitType_t'
       {aka 'tagRtLimitType'}
error: could not convert '{{LOW_POWER_TIMEOUT}, RT_LIMIT_TYPE_LOW_POWER_TIMEOUT},
       {WARP_STACK_SIZE}, ...' from '<brace-enclosed initializer list>' to ...
```

**定位过程（三步排除）**

1. 先怀疑 megatron-core（我们自己装的 0.16.1，而官方配套是 0.12.1）→ **排除**：`SIMT_WARP_STACK_SIZE` 在 megatron / mindspeed / torch_npu 里一处都搜不到
2. 再怀疑 torch_npu 与 CANN 配错 → **部分成立但非致命**：基本 NPU 张量运算完全正常（`torch.randn(8,8).npu()` 求和 = 52.785），说明环境本体健康
3. 全盘搜 `RT_LIMIT_TYPE` → **命中**：

```
/usr/local/python3.11.15/lib/python3.11/site-packages/triton/backends/ascend/npu_utils.cpp
```

**根因**：triton-ascend 在编译 Ascend kernel 之前，会现场 JIT 编译 `npu_utils.cpp`，用 `rtDeviceSetLimit()` 设置 `WARP_STACK_SIZE` / `STACK_SIZE` / `LOW_POWER_TIMEOUT` 等设备级限制。该源码引用的 `RT_LIMIT_TYPE_SIMT_WARP_STACK_SIZE` **在 CANN 9.0.0 的 `rt_external_base.h` 里不存在**（该头文件只定义到 `RT_LIMIT_TYPE_STACK_SIZE = 3`）。即 triton-ascend 3.2.0 期望比 9.0.0 更新的 CANN。

**解法分两层 —— 先绕开，再修好。**

**（1）当时（9/21）先绕开**：把两个算子实现降为纯 PyTorch 的 `eager`，让训练先跑起来。

```python
cfg["model"]["gdn_implementation"] = "eager"
cfg["model"]["causal_conv1d_implementation"] = "eager"
```

**（2）随后（9/25）证明 triton 可以修好**：该枚举只出现在 triton-ascend 自己的 `npu_utils.cpp` 里，删掉引用它的那几行即可绕过（`ascend_porting/patch_triton.py`，幂等）。打上补丁后 **`triton` 在 CANN 9.0.0 上是可用的** —— B 参考轮（`gdn=triton`）与 Conv1d 隔离实验（`conv1d=triton`）都实跑成功。

> ⚠️ **本节早期版本写过「triton 在 CANN 9.0.0 上走不通」，该结论已被推翻，勿再引用。**

该字段官方支持三档：`eager` / `triton` / `ascendc`。
- `ascendc` 性能最佳但需编译安装 `fla_npu` 算子库
- `triton` **可用**（须先打 `ascend_porting/patch_triton.py` 补丁，见上）
- `eager` 无任何额外算子依赖，作为**基线轮**配置

**副作用为正**：eager 基线 vs ascendc 优化轮的加速比，正是性能报告需要的核心对比数字。

### 问题 5：`eager` 与 `skip_*_recompute` 互斥

**现象**

```
File ".../mindspeed_mm/fsdp/models/qwen3_5/modeling_qwen3_5.py", line 2260, in overwrite_transformer_config
ValueError: skip_flash_attn_recompute cannot be True when gdn_implementation is 'eager'.
            Please set skip_flash_attn_recompute to False or use a different gdn_implementation.
```

**根因**：上游 4B 配置里 `skip_gdn_recompute` / `skip_flash_attn_recompute` 都是 `true`，这是配合 `ascendc`/`triton` 的跳过重计算优化；`gdn` 换成 eager 后不再成立。

**解法**：两个都设 `false`（同类开关，一起改，避免逐个试错）。

```python
cfg["model"]["skip_gdn_recompute"] = False
cfg["model"]["skip_flash_attn_recompute"] = False
```

## 三、两个路径陷阱

配置里用的是**相对路径**（`./ckpt/...`、`./dataset/...`），而训练时工作目录是仓库根 `MindSpeed-MM/`，所以权重和数据集必须在仓库内可见：

```bash
cd /workspace/ascend_ws/MindSpeed-MM
rmdir ckpt && ln -s /workspace/ascend_ws/ckpt ckpt
ln -s /workspace/ascend_ws/dataset dataset
```

`ckpt` 原本已存在一个**空目录**（会被误判为"已存在"而跳过建链接），必须先 `rmdir` 再建软链接。

## 四、最终可用配置要点

| 字段 | 取值 | 原因 |
|---|---|---|
| `requires-python` | `>=3.11,<3.13` | 镜像无 3.12，且不能换解释器 |
| `NON_MEGATRON` | `true` | 走插件式 FSDP2，不用 Megatron 桥接 |
| `gdn_implementation` | `eager`（基线轮）/ `triton` / `ascendc`（优化轮） | 三档都可跑：`ascendc` 需 `fla_npu` 算子库，`triton` 需先打 `ascend_porting/patch_triton.py` |
| `causal_conv1d_implementation` | 随 `gdn` 搭配；A' 隔离轮手工设为 `triton` | `gdn=ascendc` 时框架会把 `triton` 强制升级为 `triton_with_transpose` |
| `skip_gdn_recompute` | `false` | 与 eager 互斥 |
| `skip_flash_attn_recompute` | `false` | 与 eager 互斥 |
| `fully_shard_parallel_size` | `1` | 单卡轮次（全环境 2 卡） |
| `gradient_accumulation_steps` | `8` | 复现参考精度日志 |
| `max_samples` | `1000` | 复现参考精度日志 |
| `train_iters` | `100`（精度对齐轮）/ `>=200`（性能轮） | 统一性能口径取第 101–200 步 |
| `init_model_with_meta_device` | `true` | 配合 DCP 权重加载 |
| `load` | `./ckpt/dcp_path/Qwen3.5-0.8B` | `mm-convert` 转换产物 |

## 六、超时与后台任务注意事项

1. **本镜像装不了 `tmux`**：`apt-get install tmux` 报 `E: Unmet dependencies`（libc6 / libtinfo6 / python3-minimal 冲突）。**绝对不要执行 `apt --fix-broken install`** —— 会动 libc6，可能直接毁掉容器。改用 `nohup`。
2. **pip 镜像**：清华源返回 403，改用华为云 `https://repo.huaweicloud.com/repository/pypi/simple/`。
3. **终端不会自动刷新**：后台任务的输出写进日志文件，屏幕上不会有任何变化。查进度必须主动敲命令，或用第二个终端 `tail -f`。
4. **失败排查不要用 `tail`**：torchrun 失败时会打印约 25 行统一格式报告，会把真正的 Python traceback 顶出 `tail -30` 的窗口。应该用 `awk '/Traceback/{f=1} f{print}'` 抓第一个 traceback。
