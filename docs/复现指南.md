# 复现指南

> 本指南依据仓库内脚本的**实际行为**整理，说明从空环境到跑出可复算指标的全过程。
> 本项目在昇腾算力容器上实测跑通；容器惯例布局是 `/workspace/ascend_ws`，仓库内脚本默认用它作为工作根目录，**可用环境变量 `ASCEND_WORK` 覆盖**。

---

## 一、前置条件

| 项目 | 要求 |
|---|---|
| NPU | 昇腾 A2 / A3（本项目实测 Ascend910_9382，SoC `ascend910_93`，64 GB HBM） |
| CANN | 9.0.0（`/usr/local/Ascend/cann/set_env.sh`） |
| Python | 3.11.15（`/usr/local/python3.11.15/bin/python`） |
| torch / torch_npu | 2.10.0 / 2.10.0 |
| 磁盘 | ≥ 60 GB（权重约 1.7 G、数据集约 316 M、算子产物约 129 M、检查点若干） |

> `compare_accuracy.py` 与 `perf_collector.py` 是纯日志/数值处理，**CPU 环境也能跑**；其余步骤需要 NPU。

---

## 三、六步跑通

### 1. 重建软件环境

```bash
bash console/rebuild_env.sh
```

脚本固化了**实测跑通的那条路径**，不是官方文档路径。要点：

- pip 源换成华为云（清华源在本镜像返回 403）；
- 从 gitcode 克隆 MindSpeed-MM（失败回落 gitee）；
- 跑 MindSpeed-MM 自带的 `scripts/install.sh --msid eb10b92 --no`（在克隆出的框架目录内执行，**不是本仓库的脚本**）：**结尾失败是预期的**（pyproject 声明 `requires-python >=3.12` 且钉 `transformers==4.57.0`，本镜像 Python 3.11.15 必然装不上），但它的 `--msid` 步骤已先把 MindSpeed 装好；`--no` 必须带，否则无 stdin 时会陷入死循环；
- 把 `requires-python` 放宽到 `>=3.11,<3.13`（**不能升到 3.12**，否则 torch_npu 失效）；
- 用约束文件锁死 `transformers` / `torch` / `torch_npu` / `numpy` 后按名单补装依赖，再以 `--no-deps` 装 MindSpeed-MM 本体；
- 装 `triton-ascend==3.2.0`；
- 建 `ckpt` / `dataset` 软链接（配置里用的是相对路径）。

验收：`import mindspeed_mm` 通过、`mm-convert` 可用。

### 2. 恢复资产（脚本不代做）

| 资产 | 放到 | 说明 |
|---|---|---|
| HF 权重 | `ckpt/hf_path/Qwen3.5-0.8B/` | Qwen3.5-0.8B，约 1.7 G，可用 `modelscope` 拉取 |
| DCP 权重 | `ckpt/dcp_path/Qwen3.5-0.8B/` | 用 `mm-convert Qwen35Converter hf_to_dcp` 从 HF 权重转换 |
| 训练数据 | `dataset/annotations_slim.json` | 格式要求见 `skill/prepare_data.py` |

> 本项目使用的数据集为公开的 COCO2017 子集，**本仓库不附带**。`skill/prepare_data.py` 的 `random.seed(42)` 是两轮训练数据顺序一致、精度对比成立的前提，**不可删除或修改**。

### 3. 安装 AscendC 算子（`fla_npu`）

两条路线，**任选其一**：

```bash
# 路线 A：有预编译产物包 -> 约 1 分钟
bash console/restore_fla_npu.sh

# 路线 B：从源码编译 -> 25-40 分钟（需要能访问上游源码）
bash console/install_fla_npu.sh
```

路线 A 需要 `fla_npu_artifacts.tar.gz`（产物清单与打包/还原方法见 `docs/fla_npu产物清单与还原方法.md`）。脚本自带完整性校验与算子验收，任一步不过会以非 0 退出，此时改用路线 B 即可。

**验收判据（两条路线相同）**：`torch.ops.npu` 的算子条目数应远大于 **354**（354 = 一个自定义算子都没注册），且 `npu_recompute_w_u_fwd`、`npu_fast_gelu_custom`、`npu_fast_gelu_custom_backward` 三个算子都存在。

### 4. 自检

```bash
bash console/health_check.sh
```

检查 NPU 设备、Python/torch/torch_npu/transformers 版本、关键文件、`import mindspeed_mm`、`fla_npu` 是否已装、磁盘余量。

### 5. 跑一轮训练

```bash
# 基线轮（纯 PyTorch eager 实现，不需要算子库）
bash scripts/run_round.sh eager

# 优化轮（AscendC 实现，需先完成第 3 步）
bash scripts/run_round.sh ascendc
```

`run_round.sh` 会自动生成该轮的配置（`gdn_implementation` 与 `causal_conv1d_implementation` 按 mode 配对）、跑安全闸门（已有训练在跑 / 缺权重 / 选 ascendc 但没装 fla_npu 都会拒绝启动），再以 `torchrun` 后台拉起训练。

日志落在 `MindSpeed-MM/logs/train_<mode>_200.log`。

> **统一性能口径是第 101–200 步的单步耗时均值**，所以一轮至少要 200 步。

### 6. 复算指标

```bash
# 统一口径性能指标（第 101-200 步均值 + 加速比）
bash scripts/summary_metric.sh \
    MindSpeed-MM/logs/train_eager_200.log \
    MindSpeed-MM/logs/train_ascendc_200.log

# 精度对齐：四项误差统计 + 对比图
python skill/compare_accuracy.py \
    MindSpeed-MM/logs/train_eager_200.log \
    MindSpeed-MM/logs/train_ascendc_200.log \
    --output accuracy_report.json
```

两个工具都**按 `iteration` 步号锚定对齐**，而不是按日志出现顺序追加——后者会把 `loss scale: 1024.0` 这类非迭代日志当成一步 loss，导致后续所有步**静默错位**。

精度判定以**轨迹偏差（50 步滑动均值）**为主判据。原因：逐点相对误差的分母是单步瞬时 loss，而单步 loss 自身波动中位数（噪声地板）就有 16.279%，且收敛后 loss 趋近 0，**2% 这条阈值线本身落在噪声地板以下**，逐点口径不具备判定能力。详见 `docs/环境适配问题与解法.md`。

## 四、盯进度与排错

```bash
# 每分钟报一次进度，训练结束自动退出
bash console/watch_progress.sh MindSpeed-MM/logs/train_ascendc_200.log

# 日志里出现异常时，先跑这个：内置 16 种已知错误模式的匹配与解法
bash console/whats_wrong.sh MindSpeed-MM/logs/train_ascendc_200.log
```

排错时**不要用 `tail` 截断**，会丢掉真正的 traceback。完整因果链见 `docs/踩坑全记录.md` 与 `docs/环境适配问题与解法.md`。

## 五、四条容易踩的注意事项

1. **不要用 `triton` 兜底**：triton-ascend 3.2.0 的 JIT 在 CANN 9.0.0 上编译必然失败（`RT_LIMIT_TYPE_SIMT_WARP_STACK_SIZE is not a member of rtLimitType_t`），需先打 `ascend_porting/patch_triton.py`。
2. **训练期间不要传大文件或解压**：实测会造成 14–18% 的耗时噪声，加速比站不住。
3. **四轮消融必须背靠背相邻执行**，中间不插入其他任务——A→C 隔离算子替换的贡献，C→D 隔离跳过重计算的贡献，跨时段环境竞争会污染这两项对比。
4. **不同步数的轮次 loss 不可直接比较**：200 步轮的 lr 调度按总步数归一化（峰值在第 50 步），与 1000 步轮（峰值在第 100 步）不同，只比 `STEP_TIME`（与 lr 无关）。
